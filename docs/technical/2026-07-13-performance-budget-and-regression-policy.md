# PRIMAL NIGHT 성능 예산 및 회귀 방지 정책

- 상태: 초안 작성 완료, 사용자 검토 대기
- 작성일: 2026-07-13
- 적용 범위: 개발 시작부터 Steam 출시 및 출시 후 패치
- 기준 플랫폼: Windows 10·11 x86_64
- 기준 플레이: 1~2인 Steam 협동, 1080p
- 관련 설계: `docs/superpowers/specs/2026-07-13-primal-night-design.md`

## 1. 목적

이 문서는 렉, 순간 멈춤, 프레임 드랍, 메모리 증가와 네트워크 지연을 출시 직전에 발견하지 않도록 개발 단계마다 성능을 측정하고 차단하는 기준을 정의한다.

다음 원칙을 사용한다.

1. 평균 FPS만으로 통과시키지 않는다.
2. 성능 개선 전후를 같은 시드와 입력으로 비교한다.
3. CPU, GPU, 메모리, 저장, 네트워크를 분리해 측정한다.
4. 최신 프리뷰보다 최신 안정 버전을 사용한다.
5. 성능을 이유로 게임 규칙을 클라이언트마다 다르게 만들지 않는다.
6. 주석, 빈 벤치마크, 수동 체감만으로 완료 처리하지 않는다.

## 2. 고정 기술 스택

### 2.1 채택 버전

| 영역 | 채택 | 정책 |
|---|---|---|
| 엔진 | Godot 4.7 stable Standard | 프로젝트 전체에서 동일 버전 고정 |
| 스크립트 | typed GDScript | C# 혼용 금지 |
| 렌더러 | Compatibility | OpenGL 기반 저사양 우선 |
| 타일 | TileMapLayer | 시각·충돌·가림 레이어 분리 |
| 길찾기 | NavigationRegion2D / NavigationServer2D | TileMap 내비게이션 직접 사용 금지 |
| Steam | GodotSteam GDExtension | Godot 4.7 호환 명시 릴리스 고정 |
| 전송 | 최신 Steam P2P API + SDR | 구형 ISteamNetworking 금지 |
| 테스트 | GUT의 Godot 4.7 대응 버전 | 릴리스 또는 커밋 해시 고정 |
| 그래픽 | Aseprite 픽셀아트 | 런타임 PNG와 원본 분리 |
| CI | GitHub Actions + Godot headless | 로직 성능과 내보내기 검증 |
| 배포 | SteamPipe | Windows 출시 후보 검증 후 업로드 |

Godot 4.8 dev, Godot 4.7.1 RC 같은 프리뷰 버전은 사용하지 않는다. 안정 버전이라도 GodotSteam, GUT, Windows 내보내기와 저장 호환을 통과하기 전에는 업그레이드하지 않는다.

### 2.2 버전 업그레이드 게이트

엔진이나 GDExtension 업그레이드는 별도 브랜치에서 다음 항목을 모두 통과해야 한다.

- 프로젝트 전체 재임포트 후 누락 에셋 0개
- GDScript 오류·경고 증가 0개
- Windows 디버그·릴리스 내보내기 성공
- Steam 초기화, 로비, 초대, P2P, 오버레이 성공
- 기존 저장 파일 로드 성공
- 고정 벤치마크 전체 실행 성공
- 기준 대비 p95 프레임타임 악화 10% 미만
- 기준 대비 메모리 악화 10% 미만
- 30분 2인 테스트 중 연결 종료 0건

하나라도 실패하면 기존 버전을 유지한다. 최신 번호보다 검증된 조합을 우선한다.

## 3. 목표 하드웨어

### 3.1 최소 사양 목표 PC

《Project Zomboid》 공식 최소 사양과 비슷한 등급을 목표로 한다.

- 운영체제: Windows 10 64-bit
- CPU: 4코어 2.8GHz급
- RAM: 8GB
- GPU: 전용 VRAM 2GB급, OpenGL 3 호환
- 저장장치: SATA SSD
- 화면: 1920×1080
- 그래픽 설정: Low
- 목표: 일반 플레이 60fps, 최악 상황 1% Low 45fps 이상

실제 Steam 최소 사양은 이 목표 PC와 동급 또는 더 낮은 물리 장비에서 출시 후보를 측정한 뒤 확정한다. 개발자 고사양 PC의 결과만으로 최소 사양을 기재하지 않는다.

### 3.2 권장 사양 검증 PC

- CPU: 6코어급
- RAM: 16GB
- GPU: VRAM 4GB급
- 저장장치: NVMe SSD
- 화면: 1920×1080 또는 2560×1440
- 그래픽 설정: High
- 목표: 1080p 60fps 고정, 1440p 60fps 목표

### 3.3 네트워크 조건

다음 조건을 인위적으로 적용해 테스트한다.

- 정상: RTT 30ms, 손실 0%
- 일반 원격: RTT 100ms, 손실 1%
- 열악: RTT 250ms, 손실 5%, 지터 30ms

열악 조건에서 조작 반응이 늦을 수는 있지만 아이템 복제, 순간이동 누적, 세션 진행 차단과 저장 손상은 발생하면 안 된다.

## 4. 출시 성능 예산

### 4.1 프레임 예산

60fps의 한 프레임은 16.67ms다. Low 설정 최소 사양 PC에서 다음을 만족해야 한다.

| 지표 | 목표 | 차단 기준 |
|---|---:|---:|
| 평균 FPS | 60 이상 | 55 미만 |
| 1% Low | 45 이상 | 40 미만 |
| p50 프레임타임 | 16.67ms 이하 | 18.18ms 초과 |
| p95 프레임타임 | 20ms 이하 | 25ms 초과 |
| p99 프레임타임 | 22.2ms 이하 | 33.3ms 초과 |
| 50ms 이상 멈춤 | 10분당 0회 | 1회 이상 |
| 100ms 이상 멈춤 | 0회 | 즉시 실패 |

VSync를 끈 계측 결과와 실제 VSync 60 플레이 결과를 모두 보관한다. VSync가 느린 프레임을 가리는 상황을 방지한다.

### 4.2 CPU 예산

| 영역 | p95 목표 |
|---|---:|
| 전체 게임 로직 | 8ms 이하 |
| 전체 공룡 AI | 3ms 이하 |
| 길찾기 제출·반영 | 1.5ms 이하 |
| 냄새 격자 갱신 | 1ms 이하 |
| 소리 이벤트 처리 | 0.5ms 이하 |
| 인벤토리·제작·상태 | 0.5ms 이하 |
| 네트워크 직렬화·적용 | 1ms 이하 |
| 저장 스냅샷 캡처 | 한 프레임 2ms 이하 |

이 값은 매 프레임 모든 시스템이 최대치를 쓰라는 의미가 아니다. 최악의 시스템 조합에서도 전체 프레임 예산을 남기기 위한 상한이다.

### 4.3 GPU와 렌더링 예산

| 항목 | Low 목표 |
|---|---:|
| GPU p95 프레임타임 | 10ms 이하 |
| 화면 내 동적 2D 광원 | 최대 8개 |
| 화면 내 활성 파티클 | 최대 300개 |
| 드로 콜 | 600 이하 |
| 런타임 텍스처 메모리 | 768MB 이하 |
| 개별 아틀라스 | 최대 2048×2048 |
| 화면 밖 AnimatedSprite2D | 업데이트 중지 |

Compatibility 렌더러에서 지원하지 않는 고급 효과에 의존하지 않는다. 비, 안개, 혈흔은 수량 제한과 품질 옵션을 제공한다.

### 4.4 메모리 예산

| 지표 | 목표 | 차단 기준 |
|---|---:|---:|
| 게임 시작 후 작업 집합 | 1.5GB 이하 | 2GB 초과 |
| 최대 콘텐츠 상황 | 3GB 이하 | 3.5GB 초과 |
| 30분 안정 상태 증가량 | 50MB 이하 | 100MB 초과 |
| 맵 재진입 10회 후 잔류 증가 | 30MB 이하 | 75MB 초과 |
| 저장 20회 후 잔류 증가 | 10MB 이하 | 30MB 초과 |

30분 동안 계속 증가하는 메모리는 최종 수치가 예산 안이어도 누수 의심으로 실패 처리한다.

### 4.5 로딩과 저장 예산

| 동작 | 목표 | 차단 기준 |
|---|---:|---:|
| 실행부터 타이틀 | 5초 이하 | 10초 초과 |
| 새 세션 시작 | 8초 이하 | 15초 초과 |
| 저장 로드 | 5초 이하 | 10초 초과 |
| 청크 전환 끊김 | 16.67ms 이내 분산 | 50ms 이상 멈춤 |
| 저장 스냅샷 파일 쓰기 | 백그라운드 500ms 이하 | 메인 스레드 50ms 이상 차단 |

게임 플레이 중 동기 파일 I/O를 금지한다. 메인 스레드에서는 저장에 필요한 작은 불변 스냅샷만 캡처하고, 파일 쓰기는 안전한 백그라운드 단계에서 처리한다.

### 4.6 네트워크 예산

| 항목 | 목표 |
|---|---:|
| 월드 스냅샷 | 10Hz 이하 |
| 호스트 업로드 | 평균 128KB/s 이하 |
| 클라이언트 다운로드 | 평균 128KB/s 이하 |
| 단일 신뢰 메시지 | 32KB 이하 |
| 일반 RPC 페이로드 | 4KB 이하 |
| 재접속 상태 전송 | 압축 후 2MB 이하 |
| RTT 100ms 입력 반영 p95 | 180ms 이하 |
| RTT 250ms에서 진행 차단 | 0건 |

위치·방향은 최신값 우선 비신뢰 전송을 사용한다. 아이템, 피해, 제작, 목표와 저장 관련 상태는 신뢰 전송을 사용한다. 신뢰 큐에 이동 데이터를 쌓아 오래된 상태가 뒤늦게 적용되는 문제를 막는다.

## 5. 시뮬레이션 규모 상한

### 5.1 공룡

- 플레이어 근처 완전 AI: 최대 24마리
- 실제 내비게이션 추격: 동시에 최대 12마리
- 한 프레임 새 경로 요청: 최대 4개
- 먼 지역 요약 개체: 최대 100마리
- 최상위 포식자 완전 AI: 동시에 1마리

완전 AI와 요약 AI를 전환할 때 위치, 체력, 목표와 먹이 상태만 전달한다. 화면 밖 개체에 애니메이션, 충돌, 매 프레임 감지를 실행하지 않는다.

### 5.2 냄새

- 저해상도 공간 격자 사용
- 기본 갱신 빈도: 초당 4회
- 활성 구역만 갱신
- 냄새 원천을 매번 전체 검색하지 않고 등록·해제 목록으로 관리
- 바람 변화 시 전체 즉시 재계산 금지, 여러 프레임에 분산
- 화면 표시용 디버그 시각화는 출시 빌드에서 비활성화

### 5.3 소리

- 소리를 물리 오브젝트로 생성하지 않음
- 이벤트 구조체로 위치, 반경, 종류, 발생 시각만 전달
- 공간 해시로 반경 내 감지자만 조회
- 동일 위치의 반복 소리를 짧은 구간 내 병합
- 오래된 조사 소리는 즉시 폐기

### 5.4 맵 청크

- 맵을 고정 크기 청크로 분할
- 플레이어 주변 청크만 완전 활성화
- 다음 이동 방향 청크를 미리 로드
- 리소스 생성과 해제를 한 프레임에 몰지 않음
- 양 플레이어가 멀어져도 서로 다른 두 활성 영역만 유지
- 로드된 청크 상한을 넘으면 가장 오래 사용하지 않은 안전 청크 해제

## 6. 코드 작성 예방 규칙

### 6.1 매 프레임 금지 항목

다음 작업을 `_process()` 또는 `_physics_process()`에서 무조건 실행하지 않는다.

- 전체 노드 트리 검색
- `get_nodes_in_group()` 반복 호출
- 모든 공룡의 새 경로 계산
- 모든 냄새 셀 전체 순회
- JSON 인코딩·디코딩
- 파일 읽기·쓰기
- 텍스처·오디오 동적 로드
- 정규식과 긴 문자열 조립
- 반복적인 임시 Array·Dictionary 생성
- UI 전체 재구성

참조는 초기화 시 캐시하고, 이벤트가 발생했을 때만 갱신한다.

### 6.2 데이터 중심 구조

- 공룡 감지 대상은 공간 해시로 조회
- 냄새와 소리는 연속 메모리에 가까운 Packed 배열 사용 검토
- 읽기 전용 공룡·아이템 정의는 Resource로 공유
- 동일 스프라이트와 Material을 개체마다 복제하지 않음
- 반복 계산 가능한 값은 데이터 변경 시 미리 계산
- UI 문구를 만들기 위한 수치 조회와 화면 갱신을 분리

### 6.3 작업 분산

공룡 AI를 한 프레임에 모두 실행하지 않는다.

```text
프레임 0: 공룡 0, 4, 8, 12...
프레임 1: 공룡 1, 5, 9, 13...
프레임 2: 공룡 2, 6, 10, 14...
프레임 3: 공룡 3, 7, 11, 15...
```

추격 중인 가까운 공룡은 높은 빈도, 멀리 있거나 쉬는 공룡은 낮은 빈도로 실행한다. 공격 충돌과 애니메이션은 필요한 프레임 정확도를 유지한다.

### 6.4 멀티스레딩

Godot 4.7의 WorkerThreadPool은 다음과 같은 순수 데이터 계산에만 후보로 사용한다.

- 냄새 격자의 다음 상태 계산
- 저장 JSON 직렬화용 데이터 생성
- 먼 지역 생태계 요약 계산
- 경로 요청 전 후보 비용 계산

백그라운드 스레드에서 SceneTree, Node, Sprite, TileMapLayer와 UI를 직접 변경하지 않는다. 작업자는 숫자·Packed 배열·불변 스냅샷만 처리하고 결과 반영은 메인 스레드에서 한다. 스레드 도입은 단일 스레드 구현을 프로파일링한 뒤 병목이 확인된 경우에만 허용한다.

### 6.5 풀링

다음처럼 수명이 짧고 빈번한 대상만 풀링 후보로 둔다.

- 혈흔 파티클
- 발자국 데칼
- 투사체
- 일시적 소리 시각화

공룡과 아이템을 무조건 풀링하지 않는다. 프로파일러에서 생성·해제 스파이크가 확인되지 않으면 단순한 생성 수명주기를 유지한다.

## 7. 계측 구조

### 7.1 내장 도구

- Godot Profiler: 프레임, 물리, 스크립트 함수
- Visual Profiler: 렌더링 CPU·GPU 단계
- Performance 모니터: FPS, 메모리, 오브젝트, 드로 콜
- `Time.get_ticks_usec()`: 좁은 코드 구간 계측
- Remote Inspector: 런타임 노드와 리소스 상태
- 선택적 Tracy/Perfetto: 내장 프로파일러로 원인을 찾지 못한 병목

```text
PRIMAL/Save/write_usec
```

출시 빌드에서도 값 수집 자체는 매우 낮은 비용으로 유지하되, 디버그 오버레이와 파일 기록은 명시적 진단 옵션에서만 활성화한다.

### 7.3 프레임 기록

벤치마크 실행은 매 프레임 시간을 기록해 다음을 계산한다.

- 평균 FPS
- p50, p95, p99 프레임타임
- 1% Low, 0.1% Low
- 33.3ms, 50ms, 100ms 초과 프레임 수
- 최대 작업 집합과 증가 추세
- 각 커스텀 모니터의 평균·p95·최대

결과는 사람이 읽는 Markdown과 비교 가능한 JSON을 함께 생성한다.

## 9. 기준선 파일

각 기준 장비와 빌드에 다음 형식의 JSON을 저장한다.

```json
{
  "schema_version": 1,
  "engine": "4.7-stable",
  "build": "git-commit-sha",
  "hardware_id": "minimum-win10-a",
  "scenario": "B04",
  "duration_sec": 300,
  "frame_ms": {
    "p50": 15.8,
    "p95": 19.4,
    "p99": 21.7,
    "max": 28.1
  },
  "fps": {
    "average": 62.4,
    "low_1_percent": 47.8,
    "low_0_1_percent": 43.2
  },
  "stalls": {
    "over_33ms": 0,
    "over_50ms": 0,
    "over_100ms": 0
  },
  "memory_mb": {
    "start": 1320,
    "peak": 1880,
    "end": 1365
  },
  "custom": {
    "ai_update_usec_p95": 2450,
    "scent_update_usec_p95": 620,
    "navigation_requests_max_frame": 4
  }
}
```

실제 계측 프로그램이 생성하지 않은 예시 JSON을 기준선으로 복사하지 않는다. `git-commit-sha` 같은 예시 값이 남은 파일은 CI가 기준선으로 인정하지 않아야 한다.

## 10. 회귀 판정

기존 기준선과 같은 장비·시나리오에서 비교한다.

| 변화 | 경고 | PR·출시 차단 |
|---|---:|---:|
| p95 프레임타임 | +10% | +20% 또는 절대 예산 초과 |
| p99 프레임타임 | +10% | +20% 또는 절대 예산 초과 |
| 1% Low | -10% | -20% 또는 40fps 미만 |
| 최대 메모리 | +10% | +20% 또는 절대 예산 초과 |
| 30분 메모리 증가 | +25MB | +50MB 또는 지속 상승 |
| 로딩 시간 | +10% | +20% 또는 절대 예산 초과 |
| 저장 시간 | +15% | +30% 또는 메인 스레드 50ms 정지 |
| 네트워크 전송량 | +15% | +25% 또는 예산 초과 |
| 신뢰 큐 최대치 | 기준 +10 | 계속 증가하거나 입력 지연 발생 |

클라우드 CI의 GPU 수치는 장비 변동이 커서 출시 판정에 사용하지 않는다. CI는 로직 성능과 헤드리스 시뮬레이션 회귀를 차단하고, GPU·실제 프레임 판정은 고정된 물리 테스트 PC에서 수행한다.

## 11. 개발 흐름

### 기능 개발 전

1. 기능이 어떤 예산을 소비하는지 적는다.
2. 영향받는 벤치마크 ID를 선택한다.
3. 변경 전 기준선을 실행한다.

### 기능 개발 후

1. 단위·통합 테스트 실행
2. 같은 빌드 설정으로 같은 시나리오 실행
3. JSON 기준선 비교
4. 경고 발생 시 프로파일 캡처 첨부
5. 차단 발생 시 병합 금지

### 최적화 작업

1. Profiler로 CPU·GPU·I/O 중 병목 분류
2. 가장 느린 영역 하나만 변경
3. 동일 시나리오 재측정
4. 성능 이득과 코드 복잡성 비교
5. 개선되지 않으면 변경을 되돌림

프로파일 없이 “빠를 것 같은” 자료구조, 풀링, 스레드와 네이티브 확장을 도입하지 않는다.

## 13. 그래픽 옵션

Low 설정에서도 게임 규칙과 공룡 개체 수를 줄이지 않는다. 다음 시각 비용만 조절한다.

| 옵션 | Low | High |
|---|---:|---:|
| 렌더 배율 | 75% | 100% |
| 동적 광원 | 4 | 8 |
| 비 파티클 | 100 | 300 |
| 혈흔 유지 | 5분 | 세션 유지 |
| 환경 애니메이션 거리 | 1청크 | 2청크 |
| 그림자 품질 | 단순 | 상세 |
| 카메라 후처리 | 끔 | 제한 사용 |

색각 정보, 공룡 경고, 발자국과 상호작용 표시를 Low에서 제거하지 않는다.

## 14. 네트워크 성능과 보안

렉 방지를 이유로 호스트 검증을 제거하지 않는다.

- 클라이언트 명령 호출 빈도 제한
- 좌표, 거리, 쿨다운, 소유권 검증
- 비정상 대형 패킷 폐기
- 로비 구성원이 아닌 발신자 폐기
- 사용자 문자열 길이 제한
- 신뢰·비신뢰 채널 분리
- 오래된 입력과 스냅샷 폐기
- 네트워크 로그에서 IP·토큰 제외

악성 또는 고장 난 클라이언트가 반복 RPC로 호스트 프레임을 떨어뜨리지 못하도록 연결별 초당 명령 수와 페이로드 상한을 둔다.
