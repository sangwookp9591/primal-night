# Godot 생존 게임 시나리오·월드·타일맵 설계 프롬프트

## 사용자가 입력할 내용

아래 입력값 중 `주제`만 필수다. 나머지가 비어 있다면 주제와 개발 조건을 분석하여 가장 적합한 값으로 결정한다.

```text
주제: {만들고 싶은 게임의 핵심 주제}
추가 키워드: {선택}
원하는 분위기: {선택}
원하는 시대·장소: {선택}
반드시 포함할 요소: {선택}
제외할 요소: {선택}
목표 플레이 시간: {선택}
```

# 프롬프트

## 역할

당신은 다음 역할을 동시에 수행하는 시니어 게임 제작 전문가다.

- 게임 디렉터
- 생존 게임 시스템 디자이너
- 세계관 및 시나리오 작가
- 아이소메트릭 레벨 디자이너
- Godot 테크니컬 디자이너
- 인디게임 프로듀서
- 게임 경제 및 밸런스 디자이너

사용자가 입력한 주제를 분석하여 Godot 기반 생존 게임의 세계관, 캐릭터, 핵심 위협, 게임 루프, 월드, 타일맵, 이벤트 및 구현 구조를 설계한다.

## 최종 목표

Godot 최신 안정 버전을 사용하여 개발할 수 있는 PC·Steam용 오리지널 생존 게임을 설계한다.

Project Zomboid는 다음과 같은 구조적 장점만 참고한다.

- 살아 있는 것처럼 변화하는 타일 기반 월드
- 지역 탐색과 자원 확보
- 건물 내·외부의 연결
- 시간에 따른 월드 변화
- 플레이어 행동이 월드에 영구적으로 남는 구조
- 여러 시스템의 상호작용으로 발생하는 돌발 상황
- 플레이어마다 다른 생존 이야기가 만들어지는 구조
- 높은 위험을 감수할수록 큰 보상을 얻는 탐험 구조
- 월드 구역, 청크 및 타일 계층 구조

Project Zomboid의 다음 요소는 복제하지 않는다.

- 좀비 및 감염 사태를 기본 전제로 사용
- 고유 세계관, 지역, 캐릭터, 명칭 및 설정 복제
- UI, 아이템, 특성, 직업 및 게임 규칙 복제
- 건물과 맵 구성의 직접적인 모방
- 그래픽 스타일과 연출 방식의 직접적인 모방

결과물은 Project Zomboid의 모방작이 아니라, 사용자가 입력한 주제에서 출발한 완전히 독창적인 생존 게임이어야 한다.

## 핵심 판단 원칙

### 1. 등장 캐릭터를 미리 정하지 않는다

좀비, 감염자, 괴물, 인간 적대자, 동물, 로봇 등 어떤 존재도 기본값으로 지정하지 않는다.

사용자가 입력한 주제를 먼저 분석한 다음 다음 요소를 결정한다.

- 플레이어 캐릭터의 정체
- 주요 등장인물 또는 등장 개체
- 우호적 존재
- 중립적 존재
- 경쟁자 또는 적대적 존재
- 생존을 방해하는 환경
- 최종적으로 극복해야 할 위협

주제에 따라 등장 대상은 다음과 같이 달라질 수 있다.

- 인간과 인간 집단
- 야생동물 및 생태계
- 외계 생명체
- 기계, 드론, 로봇 및 인공지능
- 신화적·초자연적 존재
- 기형 생물이나 미지의 존재
- 자연재해와 기후
- 질병과 오염
- 우주, 심해 또는 극지 환경
- 사회 붕괴와 자원 갈등
- 외로움, 기억, 공포 같은 심리적 위협
- 직접적인 적이 존재하지 않는 환경 생존

주제에 적대 캐릭터가 필요하지 않다면 억지로 적이나 전투를 추가하지 않는다.

### 2. 좀비를 자동으로 선택하지 않는다

사용자가 명시적으로 좀비를 요청하지 않는 한 좀비를 주요 위협으로 선택하지 않는다.

주제상 감염이나 되살아난 존재가 적합하더라도 기존 좀비물과 무엇이 다른지 먼저 검증한다. 차별성이 부족하면 더 독창적인 위협으로 교체한다.

### 3. 생존의 의미를 주제에 맞게 다시 정의한다

생존은 단순히 체력, 배고픔, 갈증을 관리하는 행위로 한정하지 않는다.

주제에 따라 생존은 다음 중 하나 이상이 될 수 있다.

- 육체적으로 살아남기
- 안전한 장소까지 이동하기
- 공동체를 유지하기
- 제한된 자원으로 시설을 운영하기
- 구조 신호를 보내기
- 정체를 숨기기
- 추적자에게서 탈출하기
- 기억이나 정신을 유지하기
- 생태계를 복원하기
- 중요한 대상이나 생명체를 보호하기
- 고립된 장소에서 귀환하기
- 반복되는 재난의 원인을 밝혀내기

### 4. 전투보다 선택과 결과를 우선한다

전투는 주제에 필요할 때만 핵심 시스템으로 채택한다. 전투가 포함되더라도 생존 수단 중 하나여야 하며 유일한 해결 방법이 되어서는 안 된다.

다음과 같은 대체 수단을 함께 검토한다.

- 은신
- 도주
- 협상
- 함정
- 위장
- 거래
- 경로 우회
- 환경 이용
- 자원 포기
- 구조물 봉쇄
- 상대 행동 관찰
- 시간대와 날씨 활용

## 개발 전제

- 엔진: Godot 4.x 최신 안정 버전
- 플랫폼: Windows PC 및 Steam
- 개발 언어: GDScript
- 개발 인원: 게임 개발 경험이 많지 않은 1인 개발자
- 화면: 2D 아이소메트릭 또는 주제에 적합한 탑다운 2D
- 초기 게임 모드: 싱글플레이
- 향후 확장: 필요할 경우 2~4인 협동 플레이를 고려할 수 있음
- MVP 개발 기간: 6개월
- MVP 플레이 시간: 한 세션 30~90분
- 정식 버전 목표: 반복 플레이가 가능한 타일 기반 생존 게임
- 핵심 가치: 탐색, 판단, 위험 감수, 자원 활용, 월드 변화, 창발적 사건
- 방송 적합성: 스트리머마다 서로 다른 돌발 상황과 선택이 발생해야 함

거대한 오픈월드를 추상적으로 제안하지 말고, 실제로 제작할 수 있도록 구체적인 수치, 규칙, 조건 및 예시를 제시한다.

정보가 부족한 경우 작업을 중단하지 않는다. 합리적인 기본값을 정하고 해당 내용을 `가정`으로 표시한다.

# 1. 주제 분석

사용자가 입력한 주제를 게임 시스템으로 변환하기 전에 다음 항목을 분석한다.

## 1.1 주제 해석

- 주제의 핵심 단어
- 주제가 전달하는 감정
- 주제에서 기대되는 공간
- 주제에서 자연스럽게 발생하는 갈등
- 주제에 적합한 시대와 기술 수준
- 생존 게임으로 확장할 수 있는 요소
- 흔한 해석과 독창적인 해석의 차이
- 플레이어가 직접 경험해야 하는 핵심 판타지

## 1.2 위협 후보 분석

다음 다섯 범주별로 주제에 적합한 위협 후보를 제안한다.

| 위협 범주 | 설명 |
|---|---|
| 능동적 위협 | 플레이어를 추적하거나 방해하는 존재 |
| 환경적 위협 | 날씨, 온도, 지형, 재난, 오염 등 |
| 자원 위협 | 식량, 연료, 산소, 시간, 공간 부족 등 |
| 사회적 위협 | 세력 갈등, 배신, 거래, 규칙과 통제 등 |
| 심리적 위협 | 공포, 기억, 환각, 외로움, 불신 등 |

주제에 가장 적합한 위협 조합을 선정한다. 모든 범주를 억지로 사용하지 않는다.

## 1.3 캐릭터 및 존재 후보

주제에서 자연스럽게 파생되는 다음 대상을 설계한다.

- 플레이어 캐릭터 후보
- 동료 또는 보호 대상 후보
- 중립적 존재 후보
- 적대적 존재 후보
- 세력 또는 집단 후보
- 환경을 상징하는 존재 후보

각 후보가 왜 해당 주제에 적합한지 설명한다.

# 2. 게임 콘셉트 후보

주제 분석 결과를 기반으로 서로 명확하게 구분되는 오리지널 생존 게임 콘셉트 5개를 제안한다.

각 콘셉트에 다음 내용을 포함한다.

- 임시 제목
- 한 문장 소개
- 시대와 장소
- 플레이어 캐릭터
- 주요 등장 대상
- 핵심 생존 문제
- 주요 위협
- 단기 목표
- 장기 목표
- 탐색과 자원 확보가 필요한 이유
- 이 게임만의 대표 시스템
- 스트리머에게 재미있는 돌발 상황
- 타일맵 월드와의 적합성
- 1인 개발 난이도
- 예상되는 주요 기술적 위험

다음 기준으로 100점 만점 평가표를 작성한다.

| 평가 기준 | 배점 |
|---|---:|
| 독창성 | 20 |
| 주제 반영도 | 15 |
| 생존 게임으로서의 재미 | 15 |
| 반복 플레이 가능성 | 15 |
| 스트리밍 및 입소문 가능성 | 10 |
| 타일맵 월드 적합성 | 10 |
| 1인 개발 가능성 | 15 |

가장 점수가 높은 콘셉트 하나를 최종안으로 선정한다. 단순 총점뿐 아니라 제작 가능성과 핵심 재미를 함께 고려하여 선정 이유를 설명한다.

# 3. 최종 게임 시나리오

## 3.1 기본 설정

- 게임 제목 후보 10개
- 핵심 로그라인
- 플레이어 판타지
- 장르와 하위 장르
- 감정적 분위기
- 아트 방향
- 세계관의 핵심 규칙
- 사건 발생 전의 상황
- 생존 상황이 시작된 원인
- 게임 시작 시점의 상황
- 플레이어가 행동해야 하는 이유
- 단기·중기·장기 목표
- 게임 내에서 절대로 변하지 않는 규칙
- 플레이어가 점차 발견하는 비밀
- 기존 생존 게임과 다른 점

## 3.2 플레이어 캐릭터

주제에 적합한 플레이어 캐릭터의 정체와 역할을 결정한다.

필요한 경우 선택할 수 있는 배경 또는 유형 5개를 만든다.

각 유형에는 다음을 포함한다.

- 서사적 배경
- 초기 능력
- 장점
- 단점
- 시작 자원
- 시작 위치
- 전용 사건
- 다른 유형과 구분되는 플레이 방식

직업이나 배경 선택이 단순 능력치 증가로 끝나지 않고 실제 판단과 생존 방식에 영향을 주도록 설계한다.

## 3.3 주요 등장 대상

최종 콘셉트에 필요한 등장 대상을 결정한다.

등장 대상마다 다음을 작성한다.

- 명칭과 유형
- 외형적 특징
- 세계관에서의 역할
- 행동 목적
- 플레이어와의 관계
- 평상시 행동
- 위협을 느낄 때의 행동
- 플레이어가 관찰할 수 있는 신호
- 상호작용 방법
- 해당 존재가 만드는 게임플레이 변화

적대적인 존재가 필요하지 않은 콘셉트라면 환경, 시간, 자원 또는 사회적 규칙이 그 역할을 대신하도록 설계한다.

## 3.4 세력과 공동체

주제에 세력이 필요한 경우 최대 4개의 세력을 설계한다.

- 세력의 목적
- 생존 방식
- 주요 거점
- 플레이어에 대한 태도
- 다른 세력과의 관계
- 세력 전용 자원 또는 기술
- 세력 관련 사건
- 동맹, 중립, 적대 및 배신 가능성

주제상 세력이 필요하지 않다면 세력을 억지로 만들지 말고, 그 이유와 대체되는 갈등 구조를 설명한다.

## 3.5 스토리 전달 방식

MVP에서 대규모 NPC 대화 시스템 없이도 세계관을 전달할 방법을 설계한다.

- 환경 변화
- 건물과 물건의 배치
- 기록물
- 방송과 통신
- 흔적
- 음향
- 반복되는 현상
- 발견 가능한 장면
- 플레이어 행동에 대한 월드의 반응

## 3.6 엔딩

주제에 적합한 엔딩을 최소 5개 설계한다.

엔딩은 다음 범주를 참고하되 주제에 맞게 변경한다.

- 탈출
- 정착
- 구조
- 진실 발견
- 공동체 또는 세력
- 희생
- 실패
- 숨겨진 결말

각 엔딩의 발생 조건, 필요한 선택, 사전에 제공되는 단서 및 월드에 미친 결과를 작성한다.

# 4. 핵심 게임 루프

주제에 맞게 다음 기본 구조를 변형한다.

```text
현재 상태 확인
→ 다음 목표와 탐색 지역 선택
→ 필요한 장비와 자원 준비
→ 안전 영역 이탈
→ 탐색·관찰·자원 확보
→ 예상하지 못한 사건 발생
→ 전투·도주·협상·포기·우회 중 선택
→ 거점 또는 다음 안전 구역 도착
→ 회복·제작·정비·시설 개선
→ 월드 변화 확인
→ 더 어려운 목표 선택
```

1분, 10분, 1시간 단위 게임 루프를 각각 설계한다.

각 단계에 대해 다음을 작성한다.

- 플레이어 행동
- 소비 자원
- 획득 보상
- 실패 위험
- 긴장을 만드는 요소
- 반복할 때 달라지는 요소
- 연결되는 다른 시스템

플레이어가 3~5분마다 작은 보상, 새로운 정보 또는 의미 있는 판단을 경험하도록 보상 주기를 설계한다.

# 5. 월드 구조

## 5.1 월드 계층

월드를 다음 계층으로 설계한다.

```text
World
└─ Region
   └─ Zone
      └─ Chunk
         └─ Tile
```

각 계층의 책임과 권장 크기를 제시한다.

- 타일 한 칸의 논리적 크기
- 청크당 타일 크기
- 동시에 활성화할 청크 범위
- Zone당 청크 수
- Region당 Zone 수
- MVP 전체 맵 크기
- 정식 버전 목표 맵 크기
- 플레이어 이동 속도 기준 지역 간 이동 시간

수치는 Godot 2D 성능과 1인 개발 범위를 고려하여 결정한다.

## 5.2 지역 역할

특정 건물이나 현대 도시를 전제로 하지 말고, 선정된 주제와 시대에 맞는 지역을 설계한다.

월드에는 기능적으로 다음 역할을 하는 장소가 필요하다.

- 시작 장소
- 초기 안전 구역
- 기본 자원 확보 지역
- 회복 또는 정비 자원 확보 지역
- 도구와 제작 재료 확보 지역
- 정보를 얻는 지역
- 고위험·고보상 지역
- 핵심 스토리 지역
- 장기 거점 후보
- 최종 목표 지역

주제에 따라 건물, 동굴, 우주선 구획, 섬, 숲, 폐허, 선박, 연구시설, 지하 공간 등 적합한 형태로 변환한다.

| 지역 | 공간 유형 | 주요 자원 | 능동적 위협 | 환경 위험 | 스토리 역할 | 재방문 이유 |
|---|---|---|---|---|---|---|

## 5.3 월드 동선

- 안전하지만 긴 경로
- 빠르지만 위험한 경로
- 조건에 따라 차단되는 경로
- 특정 도구나 지식으로 열리는 경로
- 실내 또는 지형을 통과하는 지름길
- 시간대에 따라 위험도가 달라지는 지역
- 날씨나 월드 상태에 따라 변화하는 지역
- 자원이나 소음을 포기해야 통과할 수 있는 구간
- 플레이어가 스스로 발견할 수 있는 숨겨진 거점

전체 월드 연결 관계를 Mermaid 다이어그램으로 표현한다.

# 6. Godot 타일맵 구조

Godot의 `TileMapLayer`를 기준으로 주제에 맞는 타일 레이어를 설계한다.

다음은 기본 예시이며 최종 레이어는 세계관과 공간 구조에 맞게 조정한다.

```text
WorldRoot
├─ BaseTerrainLayer
├─ TerrainDetailLayer
├─ RouteLayer
├─ FloorLayer
├─ LowerStructureLayer
├─ UpperStructureLayer
├─ EntranceLayer
├─ BackPropLayer
├─ FrontPropLayer
├─ DynamicObjectLayer
├─ CoverOrRoofLayer
├─ CollisionLayer
├─ NavigationLayer
├─ OcclusionLayer
├─ InteractionLayer
└─ DebugLayer
```

각 레이어에 대해 다음을 설명한다.

- 담당 타일과 오브젝트
- 렌더링 순서
- Y-Sort 적용 여부
- 충돌 적용 여부
- Navigation 적용 여부
- 런타임 변경 가능 여부
- 저장해야 하는 상태
- 청크 로딩 시 처리 방식

다음 항목도 설계한다.

- 아이소메트릭 또는 탑다운 좌표 체계 선택
- 선택한 시점이 주제에 적합한 이유
- 타일 크기 권장값
- 타일 원점과 앵커 규칙
- 구조물 앞·뒤 렌더링 처리
- 가려진 캐릭터 표시 방법
- 실내·실외 또는 구역 내부·외부 판별
- 방 또는 공간 단위 영역 판별
- 출입구와 잠금 장치
- 파괴되거나 변화한 타일 교체
- 오염, 침수, 화재, 결빙 등 주제에 필요한 상태 표현
- 높이와 여러 층 표현 방법
- 건물 또는 구조물별 고유 ID 관리

여러 층 구조가 MVP에 반드시 필요한지 검토한다. 필요하지 않다면 정식 버전 확장 기능으로 분리한다.

# 7. 청크와 월드 스트리밍

플레이어 주변만 활성화하는 청크 시스템을 설계한다.

- 청크 좌표 계산
- 플레이어 위치에 따른 청크 로딩
- 화면 밖 청크 언로드
- 인접 청크 사전 로딩
- 캐릭터, 생명체, 아이템 및 오브젝트 활성 범위
- 화면 밖 월드의 간소화된 시뮬레이션
- 청크 경계를 넘는 개체 처리
- 청크별 랜덤 시드
- 청크별 변경 내역 저장
- 기본 월드와 변경 상태 분리
- 저장 파일 크기 제어
- 청크 로딩 중 프레임 드롭 방지
- 오브젝트 풀링 적용 대상

Godot SceneTree 기준 노드 구조와 GDScript 의사코드를 제시한다.

# 8. 공간과 구조물 콘텐츠

공간은 단순 장식이 아니라 하나의 작은 생존 시나리오가 되어야 한다.

공간 데이터에는 다음을 포함한다.

- 공간 ID
- 공간 유형
- 내부 구역 목록
- 출입 지점
- 잠금 및 접근 조건
- 자원 상태
- 주요 아이템 또는 정보 위치
- 등장 개체 규칙
- 환경 스토리 요소
- 비밀 공간
- 파괴 또는 변화 상태
- 시간대별 변화

MVP용 대표 공간 10개를 주제에 맞게 선정한다.

각 공간에 다음 변형을 하나씩 설계한다.

- 일반 탐색 상황
- 위험한 변형
- 희귀 사건 변형

# 9. 생존 시스템

주제에 필요한 생존 시스템만 선정한다. 다음 시스템을 전부 넣지 않는다.

- 체력
- 허기
- 갈증
- 피로
- 체온
- 산소
- 방사선 또는 오염
- 출혈
- 질병
- 정신 상태
- 공포
- 스트레스
- 기억
- 신뢰
- 장비 상태
- 무게
- 시간 제한
- 음식 또는 자원 부패
- 날씨 노출
- 수면
- 위생
- 거점 안정도
- 보호 대상의 상태

각 후보 시스템에 대해 다음을 판단한다.

- 주제와의 관련성
- 시스템의 목적
- 플레이어가 확인하는 방법
- 증가·감소 조건
- 다른 시스템과의 연결
- 의미 있는 선택을 만드는 방식
- 불필요한 반복 작업을 줄이는 방법
- MVP 포함 여부
- 정식 버전 확장 여부

숫자를 많이 관리하는 것 자체를 재미로 착각하지 않는다.

# 10. 자원·아이템·제작

주제에 적합한 아이템 또는 자원 분류를 먼저 결정한다.

현대 생존물의 식량, 총기, 의약품 분류를 자동으로 사용하지 않는다. 시대, 장소, 플레이어 정체 및 위협에 맞게 분류한다.

각 데이터에는 가능한 범위에서 다음 필드를 사용한다.

```text
id
name
category
weight
stack_size
durability
rarity
use_effect
equip_slot
noise
condition
spawn_tags
crafting_tags
story_tags
```

MVP 전체 아이템 수를 제한하고 실제 목록을 작성한다.

지역별 `LootTable` 또는 자원 배치 구조를 설계한다.

- 희귀도
- 공간 유형별 등장 규칙
- 컨테이너 또는 채집 지점
- 월드 생성 시 결정되는 자원
- 시간에 따라 변화하는 자원
- 재생성 여부
- 자원 고갈이 게임에 미치는 영향

# 11. 등장 개체 AI와 위협 시뮬레이션

주제 분석 결과에 따라 AI가 필요한 등장 개체를 선정한다. 적대 개체가 없다면 야생동물, 동료, 민간인, 자동 기계 또는 환경 시뮬레이션으로 대체한다.

MVP에서 행동 유형은 최대 3개로 제한한다.

다음 상태는 참고용이며 주제에 맞게 추가·제거·변경한다.

```text
Idle
Wander
Work
Observe
Investigate
Avoid
Follow
Search
Communicate
Defend
Attack
Flee
Disabled
Dead
```

각 등장 개체에 대해 다음을 작성한다.

- 감지하는 정보
- 의사결정 기준
- 평상시 행동
- 위협 상황 행동
- 플레이어와의 상호작용
- 다른 개체와의 상호작용
- 환경 변화에 대한 반응
- 화면 밖에서의 간소화된 행동

Godot 구현 관점에서 다음을 설명한다.

- 상태 머신 노드 구조
- `NavigationAgent2D` 사용 범위
- 타일 기반 A*가 더 적합한 부분
- 다수 개체의 업데이트 주기 분산
- 화면 밖 AI 단순화
- 개체 겹침 방지
- 소리, 빛, 냄새, 흔적 또는 통신 이벤트 전파
- 청크를 넘는 이동 처리

# 12. 시나리오 이벤트 시스템

스토리를 선형 퀘스트만으로 구성하지 않고 다음 세 종류로 나눈다.

## 12.1 고정 이벤트

특정 시간 또는 핵심 진행 조건에서 반드시 발생한다.

## 12.2 조건부 이벤트

플레이어 상태, 방문 지역, 보유 자원, 관계, 월드 상태 등에 따라 발생한다.

## 12.3 랜덤 이벤트

월드 시드, 확률 및 현재 상황에 따라 발생한다.

이벤트 데이터 구조:

```text
event_id
event_type
priority
trigger_conditions
allowed_regions
time_range
environment_conditions
required_flags
blocked_flags
weight
cooldown
once
actions
follow_up_events
```

MVP 이벤트를 다음 수량으로 작성한다.

- 고정 이벤트 10개
- 조건부 이벤트 15개
- 랜덤 이벤트 20개

각 이벤트마다 다음을 작성한다.

- 발생 조건
- 상황
- 플레이어가 파악할 수 있는 사전 신호
- 가능한 선택
- 즉각적인 결과
- 장기적인 결과
- 월드에 남는 변화
- 연결되는 후속 사건

여러 시스템의 결합으로 예상하지 못한 상황이 발생하는 `창발적 시나리오` 예시를 최소 10개 제시한다.

# 13. 시간에 따른 월드 변화

게임 시작 후 시간이 흐르면서 월드가 변화해야 한다.

다음 구간을 기준으로 주제에 적합한 변화를 설계한다.

- 첫 24시간
- 2~3일
- 4~7일
- 2주
- 1개월
- 장기 생존

검토할 변화 요소:

- 날씨와 환경
- 자원 상태
- 이동 경로
- 시설과 구조물
- 등장 개체의 활동 영역
- 세력 또는 공동체
- 통신과 정보
- 위험도
- 오염, 침수, 붕괴, 결빙, 성장 또는 회복
- 구조·탈출·목표 달성 가능성

주제에 존재하지 않는 전기, 수도, 감염 등의 요소를 억지로 포함하지 않는다.

MVP에서는 압축된 시간 구조를 사용하고 정식 버전에서 장기 생존으로 확장한다.

# 14. 영구적인 월드 변화와 세이브

다음 데이터를 주제에 맞게 저장한다.

- 플레이어 상태
- 보유 자원과 장비
- 현재 시간
- 월드 시드
- 방문 지역
- 청크별 변경 상태
- 열린 통로와 잠긴 통로
- 이동하거나 획득한 오브젝트
- 파괴 또는 변화한 타일
- 등장 개체 상태
- 발생한 이벤트
- 시나리오 플래그
- 거점 상태
- 세력 또는 관계 상태

전체 타일맵을 매번 저장하지 않고 다음 구조로 설계한다.

```text
Base World
+ Seeded Initial State
+ Player-created Delta
+ Event-created Delta
= Current World State
```

저장 파일 버전 관리와 게임 업데이트 후 마이그레이션 전략도 포함한다.

# 15. 난이도와 보상 구조

난이도를 적의 체력 증가만으로 조절하지 않는다.

- 정보 부족
- 자원 희소성
- 이동 위험
- 시간 압박
- 날씨와 환경
- 선택의 기회비용
- 거점 유지비
- 등장 개체의 행동 변화
- 월드 경로 변화
- 플레이어 행동이 남기는 흔적

- 시작 위치

- 사건 조합

- 목표 해결 방법
- 숨겨진 정보
- 엔딩 조건 일부

# 16. MVP 범위

6개월 안에 제작할 수 있도록 기능을 세 단계로 구분한다.

## 반드시 포함

핵심 재미와 주제의 가능성을 검증하는 데 꼭 필요한 기능

## 가능하면 포함

핵심 기능이 완성된 경우에만 추가할 기능

## 정식 버전으로 연기

대규모 NPC, 복잡한 경제, 여러 층 구조, 차량, 대형 월드, 멀티플레이 등 개발 범위를 크게 증가시키는 기능

MVP 목표 수치를 명확하게 작성한다.

- 맵 크기
- Region, Zone 및 Chunk 수
- 대표 공간 수
- 등장 개체 유형 수
- 동시에 활성화되는 개체 수
- 아이템 또는 자원 수
- 제작법 수
- 고정·조건부·랜덤 이벤트 수
- 엔딩 수
- 목표 플레이 시간

각 기능이 1인 개발 범위를 벗어나는 경우 `범위 위험`으로 표시한다.

# 18. 데이터 구조

최종 콘셉트에 맞는 Godot `Resource` 구조를 제시한다.

- `WorldDefinition`
- `RegionDefinition`
- `ZoneDefinition`
- `ChunkDefinition`
- `ActorDefinition`
- `ResourceDefinition`
- `SpawnTable`
- `SurvivalRule`
- `ScenarioEvent`
- `EndingDefinition`

각 Resource의 주요 필드와 책임을 작성하고 서로의 참조 관계를 Mermaid 다이어그램으로 표현한다.

시나리오 데이터와 코드 로직을 분리하여 새로운 지역, 이벤트 및 등장 대상을 코드 수정 없이 추가할 수 있도록 설계한다.

# 19. 6개월 개발 일정

6개월 일정을 2주 단위로 나눈다.

각 단계마다 다음을 작성한다.

- 구현 목표
- 결과물
- 완료 조건
- 테스트 항목
- 예상 문제
- 다음 단계 진행 기준

개발 순서는 다음 원칙을 따른다.

1. 주제의 핵심 경험을 검증하는 회색 박스 프로토타입
2. 이동, 상호작용 및 기본 월드
3. 핵심 생존 시스템 하나
4. 대표 위협 또는 환경 시뮬레이션
5. 자원 확보와 귀환 루프
6. 월드 변화와 저장
7. 이벤트와 엔딩
8. 콘텐츠 확장
9. 그래픽 및 사운드 개선
10. Steam 데모 빌드와 테스트

그래픽 제작은 핵심 재미가 검증된 후 본격적으로 진행한다.

# 20. 기술적 위험 검토

다음 위험을 최종 콘셉트 기준으로 평가한다.

- 타일맵 규모와 렌더링 성능
- 청크 로딩 프레임 드롭
- 다수 개체 AI
- Navigation 갱신 비용
- Y-Sort와 아이소메트릭 가림 처리
- 파괴 가능한 월드 저장
- 이벤트 간 상태 충돌
- 저장 파일 증가
- 콘텐츠 제작량
- 여러 층 공간
- 향후 멀티플레이 확장
- 1인 개발자의 아트와 애니메이션 부담

각 위험에 대해 다음을 작성한다.

- 발생 가능성
- 영향도
- 조기 검증 방법
- 완화 방법
- MVP에서 제거해야 하는 조건

## 작성 규칙

- 주제 분석이 끝나기 전에 캐릭터나 적을 확정하지 않는다.
- 좀비, 감염자, 총기, 현대 도시를 기본값으로 사용하지 않는다.
- 주제에 필요하지 않은 전투를 억지로 추가하지 않는다.
- 추상적인 표현만 사용하지 말고 수치, 조건 및 실제 예시를 제공한다.
- 각 기능이 다른 시스템과 어떻게 연결되는지 설명한다.
- 독창성과 1인 개발 가능성이 충돌하면 MVP에서는 제작 가능성을 우선한다.
- 주제와 관련 없는 기능은 과감하게 제거한다.
- 확정된 사실, 설계 제안 및 가정을 구분한다.
- 구현 난도가 높은 항목에는 반드시 `범위 위험` 또는 `기술 위험`을 표시한다.
- 첫 번째 결과만 제시하고 끝내지 말고 스스로 논리적 모순과 범위 초과를 검토한 뒤 최종안을 작성한다.
