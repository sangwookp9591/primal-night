## 0. 결론부터

현재 프로젝트는 **기술 회색 상자와 자동 검증 기반은 강하지만, 아직 게임의 재미를 증명한 단계는 아니다.** 감지·냄새·출혈·랩터·모닥불·도축의 연결은 차별화 가능성이 있다. 반면 시작 화면, 난이도 선택, 장비 착용, 공격, 활, 손에 든 도구 표현, 플레이어용 제작 흐름, 4인 검증은 아직 없다.

따라서 다음 방향으로 고정한다.

1. 장르는 **현대인 1~4명이 시간 균열 속 원시 생태계에 떨어지는 협동 생존·탈출 게임**이다.
2. 플레이어에게 퀘스트 목록을 주지 않는다. 추위, 흔적, 동물 반응, 망가진 현대 물건과 재료의 성질을 직접 보고 자연스럽게 학습하게 한다.
3. 서버 비용은 개발사가 부담하지 않는다. 출시 우선순위는 **싱글 → 리슨 서버 2인 안정화 → 리슨 서버 4인 검증**이며, 자체 호스팅 데디케이트 서버는 이후 선택 기능이다.
4. 착용한 옷·등 장비·주무기는 월드 캐릭터에 보여야 한다. 이를 만족하기 전에는 의상 조합별 완성 스프라이트를 대량 생산하지 않는다.
5. 먼저 20~30분짜리 3구역 수직 절편으로 재미를 증명한다. 40청크, 7일, 45개 이벤트, 10종 생물, 6개 엔딩을 동시에 만들지 않는다.
6. 4인은 최종 목표로 유지하되, `host + 3 clients` 장시간 검증 전에는 출시 사양으로 홍보하지 않는다.

## 1. GitHub 소스 재검증 결과

### 1.1 이미 강한 부분

- Godot 4.7 프로젝트이며, GUT와 여러 실제 ENet 헤드리스 하네스가 CI에 연결돼 있다. [CI 정의](https://github.com/sangwookp9591/primal-night/blob/main/.github/workflows/ci.yml)
- 출혈 → 피 냄새 → 바람 이류 → 랩터 조사/추격 → 모닥불 회피의 핵심 감지 루프가 실제 하네스로 검증된다.
- 최근 `main`에는 8방향 플레이어·랩터, 13개 아이템 스프라이트, 17개 지형 타일, 40청크 계곡 초안이 반영됐다.
- 도축은 “도구는 있는데 쓸 곳이 없고, 재료는 필요한데 얻을 곳이 없는” 모순을 해결하며 위험과 보상을 연결한다.
- 최신 검증 기록은 GUT 463개 통과와 주요 하네스 통과를 보고한다. 단, 이 문서는 GitHub 소스를 읽어 판단한 것이며 이번 검토 세션에서 Godot 바이너리로 그 결과를 독립 재실행한 것은 아니다. 에이전트는 작업 시작 시 반드시 현재 HEAD에서 다시 실행해야 한다.

### 1.2 현재 플레이어가 실제로 할 수 없는 것

[`project.godot`](https://github.com/sangwookp9591/primal-night/blob/main/project.godot)의 입력과 [`player.gd`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/player/player.gd)를 기준으로 다음이 없다.

- 일반 공격, 조준, 활 발사, 무기 교체
- 장비 착용/해제와 장비 슬롯
- 단축바와 손에 든 아이템 전환
- 싱글/호스트/참가 선택 화면
- 난이도 선택과 난이도 프리셋 적용
- 4인 세션을 플레이어가 만드는 흐름
- 컨트롤러 중심 조작과 키 재설정

현재 [`boot.gd`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/boot.gd)는 바로 메인 장면으로 진입한다. README의 조작표도 개발·디버그 키 중심이다. 즉 **자동 테스트 가능한 프로토타입이지, 처음 접한 유저가 설명 없이 플레이할 수 있는 데모는 아니다.**

### 1.3 착용 아이템이 보이지 않는 구조적 이유

현재 플레이어 장면에는 단일 `AnimatedSprite2D`만 있고, [`player_sprite_animator.gd`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/player/player_sprite_animator.gd)가 한 장의 생존자 시트를 직접 읽는다. 애니메이션도 사실상 `idle`과 `walk`이며 달리기·웅크리기는 재생 속도만 바꾼다.

[`ItemData`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/resources/item_data.gd)는 무게, 스택, 냄새, 섭취 정보만 가진다. [`Inventory`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/inventory/inventory.gd)는 `{id, count}`만 저장하고 장비 슬롯이 없다. 인벤토리 화면 역시 아이콘·수량 표시만 제공한다.

따라서 “아이템을 착용하면 외형에 보인다”는 요구는 에셋만 추가해서 해결되지 않는다. **장비 도메인, 시각 레이어, 애니메이션 동기화, 네트워크 복제**를 먼저 만들어야 한다.

### 1.4 기술 부채 다섯 항목의 현재 상태

| 항목 | 현재 판단 | 조치 |
|---|---|---|
| ENet 포트 경합 | 미해결. [`NetConfig`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/net/net_config.gd)의 기본 포트가 `8910`이고 세션 서비스도 설정 포트를 식별자로 사용한다. 병렬 테스트·빠른 재실행에서 충돌 가능 | 첫 PR에서 동적 포트와 실제 바인딩 포트 조회 도입 |
| EventBus 직접 주입 | 감지 하네스는 실제 `NoiseEmitter`와 `SmellSource` 경로를 사용하도록 개선됨 | 재구현하지 말고 회귀 테스트만 유지 |
| 냄새 강도 합산 | 가장 강한 냄새 + 나머지 일부, 상한 적용 방식으로 개선됨 | 현재 규칙을 제품 규칙으로 문서화하고 수치 플레이테스트 |
| 모닥불 레지스트리 중복 | 미해결. [`SurvivalStats`](https://github.com/sangwookp9591/primal-night/blob/main/scripts/survival/survival_stats.gd)와 랩터가 각각 `_campfires`를 보관 | 두 번째 PR에서 단일 레지스트리 도입 |
| 테스트 net 빌더 중복 | 공통 `NetTestRig`가 보이지 않고 하네스별 구축 코드가 남아 있음 | 첫 PR에서 포트 수정과 함께 공통화 |

## 2. 냉정한 구현 가능성 판단

### 가능한 것

- 싱글과 최대 4인 리슨 서버
- 유저가 직접 돌리는 헤드리스 데디케이트 서버
- 8방향 캐릭터에 옷·등 장비·손 장비를 겹쳐 표시
- 냄새·소리·바람을 이용한 사냥/회피
- 돌창과 활에서 출발해 원시 재료와 현대 지식을 결합한 한두 개의 하이브리드 장비
- 고정 퀘스트 없이 환경과 필요를 통해 해법을 알아가는 진행

### 현재 범위 그대로는 현실적으로 위험한 것

- 24주 안에 40청크, 70~90분 7일 세션, 4인 네트워크, 34개 아이템, 23개 레시피, 45개 이벤트, 10종 생물, 6개 엔딩, 저장 마이그레이션, Steam 연동을 모두 완성하는 것
- 모든 옷 조합을 완성 캐릭터 시트로 따로 그리는 것. 조합 수 × 8방향 × 행동 수 × 프레임 수로 비용이 폭발한다.
- 창·활의 타격감이 검증되지 않은 상태에서 화염방사기부터 만드는 것
- 별도 백엔드 없이 공개 서버 목록, 계정 동기화, 호스트가 나가도 이어지는 클라우드 세계, 완전한 호스트 마이그레이션까지 제공하는 것
- 테스트 통과만으로 재미와 시장성을 확정하는 것

### 반드시 지금 결정해야 하는 애매한 부분

1. **4인은 목표인가 출시 약속인가?** 목표로 유지하되 검증 관문을 통과하기 전에는 약속하지 않는다.
2. **탈출은 퀘스트인가?** 고정 부품 A/B/C 수집을 폐기한다. 세계의 상태를 바꾸는 여러 행동이 탈출 가능성을 만든다.
3. **현대 지식은 메뉴 스킬인가?** 아니다. 플레이어가 사물의 조합과 결과를 관찰해 사용하는 게임 규칙이어야 한다.
4. **화염방사기는 현실 무기 복제인가?** 아니다. 후반 만능 DPS 무기가 아니라 바람·연료·화재 확산 위험을 지닌 짧은 공간 통제 도구로 만든다.
5. **모든 소지품이 몸에 보여야 하는가?** 아니다. `outfit`, `back`, `main_hand`, 선택적으로 `head`만 월드에 보인다. 주머니 속 재료는 UI에만 표시한다.

## 3. 단단하게 고정할 콘셉트와 스토리

### 한 문장

**현대인 최대 네 명이 서로 다른 시대가 겹친 계곡에 추락해, 현대의 지식과 원시 재료를 결합하고 자신들이 남긴 냄새와 소리를 관리하며 살아서 균열을 빠져나가는 협동 생존 게임.**

### 이야기의 중심

가까운 미래, 비정상 자기장과 실종 사고를 조사하던 소형 항공기가 폭풍 속에서 사라진다. 탑승자들은 한 시대가 아니라 여러 시대의 지층과 생태가 포개진 폐쇄 계곡에서 깨어난다. 흰 나시와 흰 반바지는 구조용 검사복이자 시작 상태다. 보호력도 위장도 없고 젖으면 체온을 빼앗기므로, 첫 옷 파밍이 단순 능력치 상승이 아니라 **보이는 생존의 변화**가 된다.

계곡에는 과거 탐사대의 흔적, 너무 오래된 현대 합금, 인간을 경계하는 공룡, 반복해서 다른 위치에 나타나는 별자리와 잔해가 있다. 설명하는 NPC와 퀘스트 창은 없다. 플레이어는 무엇이 이곳을 만들었는지 단서를 조합하고, 다음 중 하나의 방향을 스스로 택한다.

- 균열을 안정시켜 모두 함께 탈출한다.
- 불안정한 균열을 강제로 열어 빠르게 탈출하지만 계곡과 동료에게 큰 위험을 남긴다.
- 계곡의 순환을 끊지 않고 살아남는 방법을 선택한다.

결말은 부품 세 개를 납품해서 열리지 않는다. 불, 전기성 광물, 고지대의 자기장, 포식자의 이동, 구조물의 상태처럼 **플레이 중 바꾼 세계 변수**가 조건이 된다.

### 퀘스트 없이 배우는 방식

- 추워지면 숫자 경고보다 숨이 하얘지고, 몸이 떨리고, 손동작이 느려진다. 멀리 보이는 따뜻한 빛과 마른 재료가 자연스럽게 해결책을 암시한다.
- 피가 나면 랩터가 바람을 거슬러 접근한다. 붕대 후 접근 경로가 달라져 플레이어가 냄새 규칙을 체감한다.
- 젖은 나무는 연기가 많고 불이 약하다. 마른 풀과 수지가 붙으면 변화가 즉시 보인다.
- 실패한 제작은 재료를 전부 삭제하지 않는다. “잘 묶이지 않는다”, “열이 부족하다” 같은 물성 피드백을 남긴다.
- 망가진 현대 물건은 완성 레시피를 주지 않고 렌즈, 코일, 압력 용기 같은 원리를 보여준다.
- 첫 10분에는 추위, 흔적, 불, 포식자 중 최소 두 규칙이 자연스럽게 연결돼야 한다.

## 4. 유저가 어렵거나 재미를 잃을 가능성이 큰 지점

| 위험 | 왜 재미를 해치는가 | 방향 결정 |
|---|---|---|
| 40청크를 먼저 채움 | 이동 시간이 선택보다 길어져 걷기 게임이 됨 | 3개 연결 구역에서 30~60초마다 판단이 생기는 밀도를 먼저 증명 |
| 숨은 냄새·바람 규칙 | 죽은 이유를 이해하지 못함 | 환경 효과, 공룡의 머리 방향, 연기, 선택형 접근성 오버레이로 피드백 |
| 순수 시행착오 제작 | 조합 폭발과 재료 손실로 공략 검색을 강요 | 물성 힌트와 실패 피드백 제공, 정답 목록은 최소화 |
| 생존 수치 4개가 빠르게 감소 | 탐험보다 게이지 노동이 됨 | 각 수치가 선택을 바꾸지 않으면 병합/삭제, 감소 주기를 길게 설정 |
| 텍스트 16칸 인벤토리 | 장비 사용과 비교가 불편 | 선택, 이동, 장착, 해제, 단축바, 장비 실루엣을 키보드·패드 모두 지원 |
| 4인일 때 적 체력만 증가 | 협동이 긴 전투로 변함 | 파티 냄새·소음, 먹이 소모, 무리 행동, 역할 분화로 난이도 조정 |
| 긴 세션과 강한 죽음 패널티 | 학습 전에 재시작 피로가 옴 | 첫 절편은 20~30분, 회수 가능한 사망과 난이도별 복구 규칙 |
| 화염 무기가 만능 | 생존·공룡 공포가 무너짐 | 짧은 사거리, 연료 희소, 역풍, 산불, 냄새·빛 유발로 공간 통제에 한정 |
| 화면에 장비 변화가 없음 | 파밍 보상이 수치로만 느껴짐 | 옷·등·손 장비는 즉시 외형 변화, 젖음·피·오염도 시각화 |

## 5. 범위 재설정: 먼저 증명할 수직 절편

| 항목 | 수직 절편 목표 | 확장 관문 통과 후 |
|---|---|---|
| 플레이 시간 | 20~30분 | 60분 이상 |
| 월드 | 밀도 높은 3구역 | 40청크 재평가 |
| 인원 | 싱글 + 2인 안정 | host + 3 clients |

| 제작 | 6~8개 | 플레이테스트에서 새 결정이 생길 때 추가 |
| 보이는 장비 | 시작 복장 포함 의상 3, 등 2, 손 장비 4 | 애니메이션 비용 측정 후 확대 |
| 전투 | 창과 활, 도망, 불로 공간 통제 | 하이브리드 화염 장비 1종 |

| 결과 | 세계 변수에 따른 3개 결과 | 서사 밀도가 유지될 때 세분화 |

## 6. 서버 비용 0원 원칙

### 출시 우선 구조

1. 싱글은 완전 오프라인으로 실행한다.
2. 협동은 플레이어 한 명이 서버도 함께 수행하는 리슨 서버다.
3. 저장 파일은 호스트 로컬에 두고, 호스트가 종료하면 세션도 종료된다.
4. 초기에는 LAN/직접 접속을 사용하고, Steam 출시 단계에서 Steam 로비·P2P/릴레이를 검토한다.
5. 개발사 소유 계정 서버, 월드 서버, 텔레메트리 서버를 필수 전제로 두지 않는다.
6. 자체 호스팅 데디케이트 서버는 같은 권위 로직을 헤드리스로 실행하는 별도 배포물로 확장한다.

### 받아들여야 할 제약

- 호스트 지연은 사실상 0에 가깝고 참가자는 호스트 네트워크 품질에 영향을 받는다.
- 호스트가 나가도 계속되는 세계와 자동 호스트 이전은 MVP에서 제공하지 않는다.
- 직접 IP 방식만 쓰면 NAT와 방화벽 때문에 참가가 어렵다. Steam 릴레이를 쓰기 전까지는 LAN과 기술 사용자용 직접 연결로 범위를 명확히 한다.
- 공개 서버 검색과 계정 간 클라우드 저장을 제공하려면 별도 비용·운영 정책이 필요하므로 “서버비 0원” 원칙과 충돌한다.

## 7. 착용 아이템을 실제 캐릭터에 보이게 만드는 설계

### 금지할 접근

`흰 나시 + 가방 + 활`, `가죽옷 + 가방 + 활`처럼 모든 조합의 완성 시트를 따로 만들지 않는다. 의상과 동작이 늘 때마다 조합 수가 곱해진다.

### 채택할 접근

플레이어 시각을 같은 방향·행동·프레임을 공유하는 레이어로 나눈다.

```text
PlayerVisualRig
├─ BaseBody       # 피부, 머리, 기본 신체
├─ Outfit         # 흰 나시·반바지, 작업복, 가죽 보호복
├─ Back           # 작은 가방, 큰 배낭
├─ MainHand       # 칼, 창, 활, 횃불
└─ StateOverlay   # 피, 젖음, 먼지, 화상
```

MVP 장비 슬롯은 `outfit`, `back`, `main_hand` 세 개로 시작하고 `head`는 이후 추가한다. 장비 정의는 최소한 다음 정보를 가진다.

- `equip_slot`
- `visual_id` 또는 `visual_profile`
- `modifiers`
- `noise_modifier`, `smell_modifier`, `wetness_modifier`
- 내구도 또는 상태 플래그

네트워크에는 텍스처 경로를 보내지 않는다. 호스트 권위의 작은 스냅샷만 복제한다.

```gdscript
{
  "outfit": &"white_underwear",
  "back": &"small_pack",
  "main_hand": &"stone_spear",
  "condition_flags": 0
}
```

### 에셋 생성 시점

1. 먼저 `EquipmentComponent`와 `PlayerVisualRig`의 임시 색상 레이어로 장착·해제·8방향 동기화를 검증한다.
2. 다음으로 시작 복장 1개, 작업복 1개, 가죽 보호복 1개만 최종 규격으로 제작한다.
3. 손 장비는 돌칼, 돌창, 활, 횃불 네 개만 만든다.
4. `idle`, `walk`, `attack`, `carry`의 프레임 규격이 고정된 뒤 추가 에셋을 생산한다.
5. `run`, `crouch`, `gather`, `hurt`, `death`는 플레이 요구 순서대로 추가한다.

### 착용 시각화 완료 기준

- 시작 시 흰 나시와 흰 반바지가 월드 캐릭터에 보인다.
- 의상을 바꾸면 같은 프레임 안에 기존 의상이 사라지고 새 의상이 표시된다.
- 창/활/횃불을 선택하면 8방향 모두 손 위치가 맞는다.
- 장착한 가방이 몸 뒤/앞 방향에 따라 올바른 `z_index`를 가진다.
- 원격 플레이어의 장비가 호스트 확정 상태와 동일하게 보인다.
- 재접속과 저장 불러오기 후 장비 상태가 복원된다.
- 없는 `visual_id`는 크래시 대신 진단 로그와 안전한 기본 외형으로 처리된다.

## 10. 시장성에 대한 냉정한 평가

### 강한 판매 포인트

- “공룡 생존” 자체보다 **내 냄새와 소리가 사냥당하는 방식**이라는 설명 가능한 차별점이 있다.
- 흰 나시·반바지에서 시작해 주운 옷과 만든 도구가 몸에 보이면 파밍 성장의 전후가 명확하다.
- 현대 지식을 원시 재료로 재현하는 장비는 영상·스트리밍에서 발견과 사고를 만들 수 있다.
- 1~4인 협동에서 한 명의 실수가 냄새·소리·불로 팀 전체 상황을 바꾸는 구조는 자연스러운 대화를 만든다.
- 개발사 서버비 없이 싱글과 친구 협동에 집중하면 작은 팀의 운영 부담을 줄일 수 있다.

### 약한 지점

- 현재 플레이 화면은 “또 하나의 생존 제작 게임”으로 보일 위험이 크다.
- 40청크와 많은 콘텐츠 수는 판매 포인트가 아니라 완성도 저하 위험이다.
- 고정 부품 수집과 UI 퀘스트를 넣으면 자율 학습이라는 핵심 약속이 무너진다.
- 장비가 보이지 않고 전투 손맛이 없으면 공룡, 파밍, 현대 지식 세 축 모두 보상감이 약하다.
- 4인 네트워크가 불안정하면 협동 게임의 평가는 콘텐츠보다 먼저 무너진다.

### 외부 홍보 전 통과할 플레이테스트 관문

- 처음 보는 플레이어 5명 중 4명 이상이 설명 없이 이동, 줍기, 불 피우기, 장착을 수행한다.
- 10분 안에 최소 한 번 “내 행동 때문에 공룡 반응이 바뀌었다”는 원인을 말할 수 있다.
- 20분 안에 창/활/불 중 두 가지 다른 해결법을 사용한다.
- 최소 3명이 다음 판에 다른 방법을 시험하고 싶다고 자발적으로 말한다.
- 2인 세션에서 강제 지시 없이 역할 분담이나 경고 대화가 발생한다.
- host + 3, 60분 soak에서 복제, 접속 해제, 아이템 소실·복제, 장비 외형 불일치 치명 오류가 0건이다.

이 관문을 통과하지 못하면 콘텐츠를 더 만들지 말고 조작, 피드백, 규칙 가독성, 결정 밀도를 고친다.

8. 화염 장비보다 창과 활의 공간 판단·회피·타격 피드백을 먼저 증명한다.
9. 자동 테스트 통과를 재미 검증으로 오해하지 않는다.
10. 관련 없는 기존 사용자 변경을 되돌리지 않는다.
